# v1.0 - Modulo de testes do novo fluxo de criacao

## Objetivo
Definir a estrategia de testes para a migracao da criacao por formulario para a experiencia com lista de bots, chat e saida tecnica.

## Escopo de testes
1. Authoring por chat.
2. Sincronizacao entre conversa e codigo.
3. Persistencia de sessao e draft.
4. Teste imediato dentro da mesma tela.
5. Regressao do runtime publicado.

## Piramide de testes

### 1. Unitarios
1. Reducers ou estado de UI da tela tripla.
2. Mapeamento de mensagens do chat para requests de backend.
3. Validacao local de dirty state.
4. Regras de reconciliacao entre conversa e codigo.
5. Validacoes de contrato antes de salvar/testar.

### 2. Integracao
1. Frontend <-> API de conversa.
2. API de authoring <-> persistencia de sessao.
3. Save de draft <-> bot_versions.
4. ad_hoc_test disparado a partir da versao em edicao.
5. Eventos de erro retornando ao fluxo de authoring.

### 3. E2E
1. Selecionar bot na coluna 1, conversar na coluna 2 e visualizar codigo na coluna 3.
2. Refinar o codigo via chat sem trocar de pagina.
3. Editar manualmente a saida e salvar draft.
4. Executar teste imediato e inspecionar resultado.
5. Aprovar/publicar a versao gerada no novo fluxo.

## Casos criticos obrigatorios
1. Troca de bot com alteracoes nao salvas.
2. Conversa com contexto incompleto gerando perguntas pendentes.
3. Divergencia entre chat e codigo editado manualmente.
4. Save de draft com contrato invalido.
5. Teste imediato com erro de import/codigo.
6. Reabertura de bot preservando contexto de authoring.
7. Falha do LLM sem perda do draft atual.

## Casos de regressao obrigatorios
1. Publicacao continua exigindo validacoes minimas.
2. Worker continua executando apenas codigo publicado/testado.
3. Scheduler nao depende do estado de authoring.
4. Logs de runtime e authoring permanecem separados.

## Dados e mocks
1. Mock de respostas do LLM para cenarios previsiveis.
2. Fixtures de bots em draft, approved e published.
3. Payloads de contract_json validos e invalidos.
4. Fixtures de runs success, fatal_error e retryable_error.

## Criterios de aceite do modulo de testes
1. Fluxos principais do redesign com cobertura automatizada.
2. Casos de perda de contexto e dirty state cobertos.
3. ad_hoc_test coberto a partir da nova tela.
4. Regressao do runtime atual protegida por testes.

## Gate sugerido antes de liberar a mudanca
1. Testes unitarios do frontend passando.
2. Testes de integracao do backend de authoring passando.
3. Pelo menos 3 cenarios E2E verdes.
4. Smoke test manual da tela tripla em desktop.
5. Checklist de seguranca e segredos revisado.
