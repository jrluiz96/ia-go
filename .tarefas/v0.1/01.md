## Decisão de arquitetura: criação, save e execução de robôs

Sua linha de raciocínio está correta, mas com um ajuste importante: não salvar "thread em memória" como estratégia principal.

### Correcao de escopo (decisao oficial)

1. IA entra apenas na fase de criacao e manutencao do bot Python.
2. Depois de aprovado/publicado, o bot roda em producao sem IA no loop de execucao.
3. Execucao de producao deve ser deterministica: scheduler + fila + worker + regras fixas de retry.
4. Analise por IA de execucao (logs/runs) nao faz parte do caminho critico do runtime.

### 1) Tela de criação (linguagem natural + teste imediato)

- O usuário descreve a automação em linguagem natural.
- A IA gera o script Python + metadados de execução.
- O botão de teste executa uma execução efêmera (não agendada), com timeout curto e logs em tempo real.

### 2) O que salvar no Save do robô

No Save do robô pronto, salvar no PostgreSQL:

1. Definição do robô (nome, descrição, dono, tags).
2. Código-fonte Python versionado (ou referência para artefato versionado).
3. Contrato de execução (schema JSON de entrada/saída, timeouts, retries, capacidades exigidas).
4. Agendamento (cron, fuso horário, janela permitida).
5. Política de execução (concorrência máxima por robô, deduplicação, prioridade).

Resumo: sim, deve salvar tanto o código Python quanto o contrato de execução.

### 3) Processador de robôs (scheduler + dispatcher)

Em vez de "loop que sobe thread", use este fluxo:

1. Scheduler: identifica jobs vencidos pelo agendamento.
2. Dispatcher: cria uma instância de execução e publica em fila.
3. Worker: consome da fila e executa o robô (Python).
4. Reporter: atualiza status, logs, métricas e resultado.

### 4) Por que não depender de thread local

- Thread local funciona no início, mas perde confiabilidade em reinício do processo.
- Fila + workers permite retry seguro, escala horizontal e isolamento de falhas.
- Evita execução duplicada com mecanismos de lock/idempotência.

### 5) Modelo mínimo de tabelas (v0.1)

1. bots
- id, name, description, owner_id, active, created_at, updated_at

2. bot_versions
- id, bot_id, version, code_python, contract_json, created_at

3. bot_schedules
- id, bot_id, cron_expr, timezone, next_run_at, enabled

4. bot_runs
- id, bot_id, bot_version_id, scheduled_at, started_at, finished_at
- status (queued/running/success/retryable_error/fatal_error/canceled)
- input_json, output_json, error_code, error_message, worker_id, trace_id

5. run_events (opcional na v0.1, mas útil)
- id, run_id, ts, level, message, data_json

### 6) Contrato Go <-> Python (estável e versionado)

Entrada (Go -> Worker Python):

- contract_version
- run_id
- bot_id
- bot_version
- params
- timeout_sec
- trace_id
- capabilities (ex: windows_cert_store=true, headless_browser=true)

Saída (Python -> Go):

- run_id
- status: success | retryable_error | fatal_error
- result
- artifacts (prints, html, json)
- error_code
- error_message
- metrics (duration_ms, steps)

### 7) Roteamento de execução por capacidade

Defina capacidades do job para escolher o ambiente:

1. web_headless_only -> worker Linux container.
2. needs_windows_cert_store -> worker Windows host.
3. needs_gui_desktop -> worker Windows com sessão interativa.

### 8) Execução de teste imediato (na criação)

Para o botão de teste:

1. Cria run_type = ad_hoc_test.
2. Não agenda em cron.
3. Timeout menor (ex: 60-180s).
4. Retorno direto para UI com logs e resultado.

### 9) Estratégia incremental recomendada

Fase 1 (simples e funcional):

1. Scheduler no Go.
2. Fila (Redis/RabbitMQ).
3. Worker Python único.
4. Persistência completa de bot_runs.

Fase 2 (escala e robustez):

1. Múltiplos workers por capacidade (Linux/Windows).
2. Retry com backoff exponencial.
3. Idempotência forte por run_id.
4. Observabilidade (logs estruturados + métricas).

## Resposta direta da sua pergunta

- Sim, salvar código Python no banco (ou referência versionada) faz sentido na v0.1.
- Sim, salvar contrato de execução junto é obrigatório para estabilidade.
- O processador não deve só "subir thread"; o ideal é scheduler + fila + worker.
- Thread em memória pode existir para protótipo local, mas não como base de produção.

## Contrato de execução v1 (Go -> Python -> Go)

Objetivo: permitir execução automática sem prompts de login, com credenciais seguras e contrato estável.

### 1) Envelope de entrada (Go -> Worker Python)

Campos obrigatórios:

1. contract_version
2. run_id
3. bot_id
4. bot_version
5. run_type
6. params
7. auth_profile
8. execution_context
9. retry_policy
10. trace

Exemplo:

```json
{
	"contract_version": "1.0",
	"run_id": "run_20260505_0001",
	"bot_id": "bot_sales_portal",
	"bot_version": 3,
	"run_type": "scheduled",
	"params": {
		"base_url": "https://portal.exemplo.com",
		"empresa": "ACME",
		"periodo": "2026-05"
	},
	"auth_profile": {
		"type": "basic_login",
		"credential_ref": {
			"provider": "vault",
			"secret_id": "cred_sales_portal_prod"
		},
		"session_policy": {
			"reuse_session": true,
			"max_age_minutes": 480
		}
	},
	"execution_context": {
		"target": "linux_headless",
		"timeout_sec": 300,
		"timezone": "America/Sao_Paulo",
		"artifacts": {
			"screenshot_on_error": true,
			"save_html_on_error": true,
			"save_har": false
		},
		"capabilities": {
			"web_headless_only": true,
			"needs_windows_cert_store": false,
			"needs_gui_desktop": false
		}
	},
	"retry_policy": {
		"max_attempts": 3,
		"backoff": "exponential",
		"base_delay_sec": 10,
		"max_delay_sec": 180
	},
	"trace": {
		"trace_id": "tr_7f13af8",
		"tenant_id": "tenant_default",
		"requested_by": "scheduler"
	}
}
```

### 2) Envelope de saída (Worker Python -> Go)

Campos obrigatórios:

1. contract_version
2. run_id
3. status
4. timestamps
5. metrics

Campos condicionais:

1. result (quando success)
2. error (quando retryable_error ou fatal_error)
3. artifacts (opcional)

Exemplo:

```json
{
	"contract_version": "1.0",
	"run_id": "run_20260505_0001",
	"status": "success",
	"timestamps": {
		"started_at": "2026-05-05T10:00:01Z",
		"finished_at": "2026-05-05T10:01:32Z"
	},
	"metrics": {
		"duration_ms": 91000,
		"steps": 24,
		"retries_used": 0
	},
	"result": {
		"records_collected": 152,
		"output_ref": "s3://ia-go/runs/run_20260505_0001/result.json"
	},
	"artifacts": {
		"screenshots": [],
		"html": [],
		"logs_ref": "s3://ia-go/runs/run_20260505_0001/logs.ndjson"
	}
}
```

Exemplo de erro transitório:

```json
{
	"contract_version": "1.0",
	"run_id": "run_20260505_0001",
	"status": "retryable_error",
	"timestamps": {
		"started_at": "2026-05-05T10:00:01Z",
		"finished_at": "2026-05-05T10:00:35Z"
	},
	"metrics": {
		"duration_ms": 34000,
		"steps": 9,
		"retries_used": 1
	},
	"error": {
		"code": "AUTH_SESSION_EXPIRED",
		"message": "Sessao expirada durante navegacao",
		"detail": "Token retornou 401 na rota /dashboard"
	}
}
```

### 3) Tipos de autenticacao suportados no v1

1. basic_login: usuario/senha via credential_ref.
2. bearer_token: token via credential_ref.
3. client_cert_file: caminho de certificado A1 + senha via secret.
4. windows_cert_store: certificado do store do Windows (worker Windows).

Observacao: para nao ficar perguntando login, sempre usar credential_ref e nunca senha literal no contrato.

### 4) Politica de seguranca

1. Nao persistir segredo em bot_versions.contract_json.
2. Persistir apenas referencia (secret_id).
3. Mascarar campos sensiveis em logs.
4. Criptografar dados sensiveis em repouso.
5. Bloquear retorno de segredo no envelope de saida.

### 5) Validacoes obrigatorias no backend Go

1. Validar contract_version.
2. Validar presenca de todos os obrigatorios.
3. Validar compatibilidade de capabilities x target.
4. Validar timeout_sec (faixa segura, ex: 30 a 3600).
5. Validar retry_policy (max_attempts <= 5 na v1).
6. Rejeitar contrato com segredo inline (regex de senha/token em claro).

### 6) Estados de execucao padrao

1. queued
2. running
3. success
4. retryable_error
5. fatal_error
6. canceled

Mapeamento recomendado:

1. retryable_error -> aplica retry com backoff.
2. fatal_error -> encerra run sem retry.

### 7) Heartbeat para deteccao de travamento

Durante running, worker envia heartbeat (ex: a cada 15s) contendo:

1. run_id
2. ts
3. step
4. progress_pct

Se passar limite sem heartbeat (ex: 60s), backend marca run como possivel travado e aciona cancelamento/reatribuicao conforme politica.

### 8) Contrato para teste imediato na UI

Para run_type = ad_hoc_test:

1. timeout menor (60-180s)
2. max_attempts = 1
3. retorno sincronizado para UI com logs resumidos
4. artifacts opcionais para depuracao rapida

### 9) Decisao de armazenamento no PostgreSQL

Em bot_versions:

1. code_python: texto do codigo (ou referencia para storage de artefato).
2. contract_template_json: contrato base sem segredos.
3. schema_version: versao do contrato.

Em bot_runs:

1. input_json: envelope resolvido da execucao (com secret_id, sem segredo).
2. output_json: envelope de saida.
3. status/error_code/error_message.

### 10) Regra de ouro para login sem prompt

1. Cadastro de credencial e validacao no momento de configuracao do robo.
2. Save guarda somente credential_ref (secret_id).
3. Execucao resolve segredo automaticamente no worker.
4. Em caso de credencial invalida/expirada, retornar code especifico (AUTH_CREDENTIAL_INVALID) e notificar para recadastro.

## Ciclo de vida do bot (estado oficial)

Objetivo: separar claramente fase de autoria (com IA) da fase de runtime (sem IA).

### Estados

1. draft
- Bot em edicao. Pode receber geracao/refino por IA.

2. tested
- Bot passou em teste imediato (ad_hoc_test) com criterios minimos.

3. approved
- Revisao humana concluida. Pronto para publicar.

4. published
- Versao ativa para execucao em fila (scheduler/worker), sem IA no runtime.

5. paused
- Publicado, mas temporariamente sem disparo de novas execucoes.

6. deprecated
- Versao aposentada. Nao recebe novas execucoes.

7. archived
- Estado final historico. Apenas consulta/auditoria.

### Transicoes permitidas

1. draft -> tested
2. tested -> draft
3. tested -> approved
4. approved -> published
5. published -> paused
6. paused -> published
7. published -> deprecated
8. paused -> deprecated
9. deprecated -> archived

Transicoes bloqueadas (exemplos):

1. draft -> published (proibido pular validacao/aprovacao)
2. published -> draft (exigir nova versao)
3. archived -> qualquer outro estado

### Regras de guarda por transicao

Para ir para tested:

1. Contrato v1 valido.
2. Credencial referenciada (secret_id) valida para ambiente alvo.
3. ad_hoc_test com status success ou percentual minimo de checks configurado.

Para ir para approved:

1. Testes minimos presentes (contrato + fluxo feliz).
2. Revisao manual de codigo concluida.
3. Sem segredo em texto puro detectado.

Para ir para published:

1. approved = true.
2. Agendamento valido (cron/timezone) quando aplicavel.
3. target/capabilities compativeis com worker disponivel.

Para ir para deprecated:

1. Sem runs em estado running para a versao, ou com janela de drenagem concluida.

### Versionamento e rollout

1. Nao editar versao publicada em lugar.
2. Toda alteracao relevante cria nova bot_version.
3. Publicacao promove apenas uma versao ativa por bot (na v0.1).
4. Rollback = republicar versao anterior aprovada.

### Campos recomendados no PostgreSQL

Em bots:

1. lifecycle_state
2. current_version_id
3. approved_by
4. approved_at
5. published_at
6. deprecated_at

Em bot_versions:

1. state (draft/tested/approved/published/paused/deprecated/archived)
2. test_report_json
3. review_notes
4. published_by

### Regras de runtime alinhadas ao escopo

1. Apenas versoes em published podem gerar novas runs agendadas.
2. paused bloqueia novos disparos, mas permite finalizar runs ja iniciadas.
3. Runtime nao consulta IA para decidir retry/erro/roteamento.
4. Falhas seguem regras deterministicas do contrato e do scheduler.
